## Findings

### 1. P2 — Tracker deduplication key disagrees with the emitted path, double-counting trailing-slash navigation

**Location:** `public/tracker.js:52-58` (`path()` — strips query, collapses trailing slashes, optionally redacts) versus `public/tracker.js:122-126` (`pageview()` dedupes on raw `location.pathname` and stores it in `lastPage`).

**Defect.** In aggregate and attribution modes alike, an in-app navigation that only changes the trailing slash (`/about` → `/about/`) produces a distinct `location.pathname`, so the dedupe check passes, yet the emitted event carries the identical normalized path `/about`. `analytics_events.id` is a fresh UUID per emission, so the collector has no way to collapse the pair: pageview totals, the session's `pageviews` counter, the bounce gate (`pageviews=1 AND goals=0`, `apps/worker/reports.ts:89`) and exit-page attribution all inflate, while the dashboard shows two pageviews at one path that the client itself treats as if both were the same page. The peer fix for redacted paths already went in the opposite direction (raw key) so distinct routes are not collapsed; the residual case is the mirror image: the raw key lets equivalent normalized routes through the dedupe. `location.pathname` never contains a query string, so trailing-slash collapsing is the only normalization difference.

**Reproduction (executed).** Node VM executing the pinned `/tmp/analytica-head/public/tracker.js` with a stub DOM/location/history (`/tmp/analytica-head/tracker-repro.mjs`): initial load emits one `pageview` with `path:'/about'`; `history.pushState('/about/')` then emits a second event whose `path` also reads `/about`; `pushState('/checkout')` correctly emits once. The existing browser flow `tests/browser/app.spec.ts:67` covers queued opt-out and redaction but not a trailing-slash pushState pair, which is why this survived the 2026 peer fixes.

**Suggested fix and test.** Normalize the dedupe key exactly like the emitted non-redacted path — `lastPage = location.pathname.replace(/\/+$/,'') || '/'` — while keeping the un-normalized raw pathname as the in-memory navigation key only when `data-redact-path` is set (that case must keep distinguishing routes). Then add a Chromium fixture: initial load of `/docs`, `pushState('/docs/')`, and `pushState('/checkout')` expect pageviews `['/docs','/checkout']` and total count 2; assert the fixture also under `data-redact-path` where two distinct raw routes still yield two redacted pageviews.

### 2. P3 — Paused or deleting sites answer money webhooks with a misleading 404, and an in-flight pause race surfaces an unclassified 500

**Location:** `apps/worker/revenue.ts:158-184` (webhook route), `apps/worker/revenue.ts:121-126` + `migrations/0002_revenue.sql:72-80` (trigger recheck inside the insert transaction).

**Defect.** The webhook handler resolves the integration with `s.status='active'` (`revenue.ts:159`). For a **paused** site the payload is then rejected with `{error:'integration_not_found'},404` — a status that tells an operator/integrator nothing about the pause and that payment providers may interpret as a permanent misconfiguration, ending retries; the same holds for a deleting site. Consequence: while a site is paused (measurement hygiene), `payment.succeeded` and `refund.succeeded` deliveries silently depend on the provider's retry window; once exhausted, those transactions never appear in revenue and no local trace exists. Worse, in the narrow window where the site flips from active to paused or deleting *between* the handler SELECT (`:159`) and the insert batch, the trigger raise (`'site_inactive'`) passes through the catch unmatched — the classification regex at `revenue.ts:182` (unlike the server-API regex at `:131`, which does cover it) — so the response becomes an unclassified 500 `request_failed`. I verified statically that `paused` appears nowhere in the test suite; Dodo's delivery retry policy is already an open release gate, and this finding concerns what the *local code* tells the provider and the operator in the meantime.

**Suggested fix and test.** Distinguish the states: a paused site should answer with a classified body, for example `{error:'site_paused'}`, keeping the response non-2xx so provider retries continue, and the webhook catch should map `site_inactive`/`key_revoked_or_site_inactive` to that classified response instead of the bare throw; document on the payments page that pausing stops money intake and that deliveries exceeding the provider's retry window are unrecoverable. Add a worker fixture: site paused → signed `payment.succeeded` webhook → assert the classified error body (distinct from `integration_not_found`); flip the site to restoring between the handler SELECT and the batch (a concurrent request) → assert the same classified body, so a paused-site delivery can be diagnosed in the Dodo sandbox without guessing at a generic 500.

### 3. P3 — Erasure requests mint permanent suppression and journal rows for visitor IDs that never existed, and the journal export silently outgrows its own limit

**Location:** `apps/worker/privacy.ts:98-110` (erasure endpoint accepts any `validId` visitor, 8-80 arbitrary chars), `apps/worker/privacy.ts:39-53` (suppression × journal × job × dirty buckets in one batch, no existence precheck), `apps/worker/privacy.ts:111-117` (journal export fails once more than 1,000 records exist).

**Defect.** Erasure is a database write for every accepted call, whether or not the visitor ever generated data. Because `visitor_suppressions` rows are intentionally never removed (they must outlive tombstones, per the comment at `migrations/0003_privacy.sql:2-4`) and each distinct visitor erasure adds a `privacy_journal` + `privacy_jobs` pair, repeated calls with arbitrary 8-80 character IDs accumulate one permanent row set per call — anonymous API garbage stored beside real erasure evidence in the same forensics journal, with no way to reclaim it. This matters operationally: the workspace journal API export is capped at 1,000 records (`privacy.ts:112-113` returns 413 above that), so a journal-heavy workspace permanently loses the API export path and is pushed to the off-database operator D1 export for every recovery need from then on.

**Suggested fix and test.** Admit erasure only against retained evidence: one `EXISTS(SELECT 1 FROM analytics_events ... OR analytics_sessions ...)` precheck (or an equivalent cheap admission query) that returns a typed 404 `visitor_not_found` for never-seen IDs, so random-ID noise creates zero rows; alternatively keep intake open but route no-op visitor jobs after completion into a bounded prune list. Add a fixture: erasure of a nonexistent visitor creates zero suppression/journal/job rows and returns a distinct status; a workspace with 1,005 rows produces a successful journal export through the bounded re-apply path.

### 4. N — Informational notes from the same inspection

- **`apps/worker/revenue.ts:131/182` classification asymmetry** (aside from finding 2): the server-side money API maps `site_inactive|key_revoked` to 409, the webhook path does not — the mapping regexes drifted from each other; consolidate them into one exported constant list.
- **`apps/worker/analytics.ts:137/158` partial-session boundary semantics**: `sessions`/`bounceRate` cover only sessions *started* within the range, while events that cross either range boundary all count in that range's totals, so a session that straddles the period border can contribute pageviews without raising the session or bounce denominators. The report's coverage string explains aggregation semantics but not this boundary rule; one added sentence (or a fixture near `tests/analytics.test.ts:183`) would document it.
- **`apps/worker/reports.ts:45` vs `apps/worker/maintenance.ts:37`**: retention removes events at `received_at < now-90d` while the report range validates `from >= now-91d`, so a 91-day-wide custom range can render a shortfall on the oldest day without error (the coverage string discloses 90-day retention only generically). Not a correctness bug, but tightening the validation to `now-90*DAY` (or the customer-visible note) removes the one-silent-day case.
- **Key cap race**: `apps/worker/revenue.ts:56-57` counts active keys before an unguarded INSERT, so concurrent creations can exceed the 10-key cap by one or more; admin-only, low impact. A trigger shaped like `funnel_admission` (`migrations/0004_funnels.sql:11-16`) would match the codebase's own cap pattern.
- **`apps/worker/revenue.ts:138`**: `checkouts` accepts `visitor_id`/`session_id` without validating their `8-80` shape (unlike every other identifier import), bound later in the session lookup; consistent validation would make the claim rows uniformly parseable in forensics exports. Low value; style-consistency only.
- **`apps/worker/auth.ts:123-126`**: every authentication call runs two extra `DELETE ... LIMIT 8` statements against `auth_challenges`/`auth_rate_limits`. Functionally fine; writes charged per auth request are worth the single measurement line in the CPU/write gate already recorded for `docs/operations/release-status.md`.

## Areas reviewed without rising to findings

- **Auth/authorization:** passkey registration, login counter-lockout and challenge consumption (`apps/worker/auth.ts:118-136,204-283,343-378`) are admitted atomically through marker-token SQL gates in one batch, which also prevents one-owner races, cross-origin challenge repointing (origin/rpID rebound at `:188-189`), and reusable proofs. Membership removal (`:476-481`) does not revoke the removed user's sessions, but every downstream check (`requireWorkspace`, `principal`) consults membership/`disabled_at` per request, so revocation is authoritative without session churn. Recovery code rotation is single-transaction (`:238,278`). Session cookies are `SameSite=Strict`, HttpOnly, 7 days with server-side rows; secret comparison is HMAC digest-based.
- **Ingestion atomicity:** site status, immutable configuration, quotas (site + installation), session identity/inactivity and late-event rejection all run inside the `BEFORE INSERT` trigger under the caller's own insert transaction (`migrations/0001_analytics.sql:106-122`); derived session/usage/bucket mutations roll back with any trigger abort (`0001_analytics.sql:124-154`, covered by `tests/analytics.test.ts:18-36,77,216-252`). Quota reads and increments are serialized by D1 as designed; a duplicate delivery legitimately bypasses admission yet legitimately never double-charges (the `ON CONFLICT DO NOTHING` row does not run the after-trigger, verified by the suite).
- **Money idempotency/checkout trust:** economic fingerprinting excludes just the omitted timestamp and re-checks digests both before and after insert (`apps/worker/revenue.ts:104-126`), claim consumption is re-validated by trigger inside the insert transaction (`0002_revenue.sql:74,82-84`), refund amount/currency legality is cumulative and quarantined at query time rather than silently credited (`0002_revenue.sql:75-79`, `apps/worker/revenue.ts:193-195`), checkout claims only mint on a server-authenticated key with consent-scoped active sessions plus a verified last-non-direct snapshot (`apps/worker/revenue.ts:133-147`), and the webhook signature covers the raw body with a ±300 s window and multi-signature parsing (`apps/worker/revenue.ts:150-157`).
- **Retention vs summaries:** the 90-day detail/396-day summary split in `apps/worker/maintenance.ts:34-42` and the dirty-bucket obligation exist correctly; raw `daily_summaries` are deliberately unused by reports today (documented as future additive-reporting material in `docs/decisions/atomic-ingestion.md:41`), so I do not treat the rebuild writes as a defect.
