# Analytics implementation review

Reviewed 26 October 2026 by the implementation sub-agent using the current GPT-6.1 Sol provider context. This is a focused, read-only review of collector/report/maintenance integration, the tracker, and financial retention. I wrote only this report. The parent is concurrently fixing findings, so line references describe the inspected snapshot rather than asserting that a fix is still absent.

Existing local Worker/D1 tests were already passing. For two tracker findings I additionally executed the shipped script in an isolated Node VM with a minimal DOM and captured outgoing fetch payloads. No remote deployment or account was used.

## P1 findings

1. **Deleting-site cleanup permanently starves the third site.** `apps/worker/maintenance.ts:29-32` selects `sites WHERE status='deleting' LIMIT 2`, and intentionally preserves those sites as tombstones. `apps/worker/revenue.ts:208-214` repeats the same selection. Once two sites are fully emptied, they remain the first selected rows on every run; any additional deleting site can retain analytics and payment records forever. Finalize/remove completed tombstones after all domain tables finish, or select only sites with outstanding work/use a fair persistent checkpoint. Test three or more sites through repeated cron runs and verify that all lose their records.

2. **A queued opt-out still sends the first pageview.** `public/tracker.js:181-182` calls `pageview(false)` before processing commands saved in `window.analytica.q`. In aggregate mode, measurement starts enabled. A site that queues `['optOut', true]` before the script loads therefore emits a pageview before the known opt-out executes. The isolated VM captured exactly `['pageview']` for that setup. Apply queued consent/opt-out configuration before any automatic collection; verify zero fetches/beacons/cookies for a prequeued opt-out.

3. **Retention changes a recent confirmed refund into an unmatched pending record.** `apps/worker/revenue.ts:190-200` derives refund validity and its acquisition snapshot by joining the original `money_records` payment. `cleanupRevenue`, line 219 in the inspected version, deletes old payments by their own `received_at` without considering still-retained refunds. Example: payment on day 0, valid partial refund on day 395, cleanup on day 397. The payment expires while the refund remains. The report now sees no original, labels that previously confirmed refund pending, removes it from refunded/net totals, and loses its source. Retain the minimal original while a retained refund depends on it, or persist independently validated original/currency/attribution evidence on the refund. Advance the fixture across both retention boundaries and reconcile totals.

## P2 findings

4. **Full path redaction suppresses legitimate SPA pageviews.** `public/tracker.js:52-57` returns the same `/[redacted]` path for every route with `data-redact-path`. Lines 122-123 use that redacted value as the navigation deduplication key. A new SPA route is therefore indistinguishable from a duplicate. The isolated VM observed one pageview across initial load plus `pushState('/second')`. Compare an in-memory raw navigation key while emitting only the redacted path; test that two different route transitions yield two redacted pageviews without leaking either path.

5. **Event filtering empties traffic reports instead of selecting the matching sessions.** `apps/worker/reports.ts:55-63` constrains every selected event to `name=? AND type='goal'`. The source/page/country/device breakdowns then add `type='pageview'` at lines 81-85, making those queries impossible. An existing signup goal thus produces zero pageviews and empty acquisition/pages while the app displays "No visits in this period" at `apps/dashboard/App.tsx:177`. If the global Event filter means sessions that completed the goal, use a scoped `EXISTS` subquery and keep pageviews from those sessions. Otherwise change the product contract and UI to clearly label an event-only view rather than implying no traffic. Add a pageview plus signup fixture and exercise the actual event filter.

6. **The promised 30-day last non-direct attribution is not implemented.** `apps/worker/revenue.ts:139-145` copies source/channel/campaign from the submitted checkout session directly. No preceding non-direct session for that visitor is consulted. A visitor acquired through a newsletter who returns directly before checkout gets a Direct financial snapshot, despite the implementation plan's explicit last non-direct rule. At trusted checkout issuance, select the eligible preceding non-direct session within the documented 30-day window, retain its ID/evidence time/model version in the minimal immutable snapshot, and fall back to the current direct session only when no eligible non-direct evidence exists. Test the direct return and window-expiry cases.

7. **Session attribution and event attribution can diverge during concurrent first delivery.** `apps/worker/analytics.ts:106-111` loads existing session attribution before the event's atomic insert. Two first events for one session can both see no session, choose different event-level sources, and then race. `analytics_event_accepted` freezes session source from the winner, but the losing event retains its separately chosen source. Reports aggregate `analytics_events.source`, while checkout issuance copies `analytics_sessions.source`, so acquisition and financial attribution can disagree for the same session. Derive the final source from authoritative session state within the atomic insert/trigger, or query reports through the frozen session attribution consistently. Test concurrent first pageview/goal deliveries with different source inputs and require one frozen source across both records.
