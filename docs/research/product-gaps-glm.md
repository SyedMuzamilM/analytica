## Confirmed remaining concrete flaws [1]

Small, verified against current source; none is P1. They are separated from missing capabilities below.

1. **`quota_exceeded` collapses two different limiters, and no surface ever shows the limits.** The insert trigger distinguishes `site_quota_exceeded` (per-site `daily_limit`, default 1,000, site CHECK + `daily_limit` column populated as hardcoded `1000` in `apps/worker/analytics.ts:454`) from `installation_quota_exceeded` (2,000/installation/day, same migration). But the collect handler matches `/quota_exceeded/` and returns a single `{"error":"quota_exceeded"}` with `Retry-After: 3600` (`apps/worker/analytics.ts:378-381`). The customer cannot tell which cap tripped, and the dashboard never displays `dailyLimit` or current usage (`daily_usage`/`installation_usage` have no read route; `App.tsx` surfaces only `Last event <time>` around `App.tsx:1531-1533`; grep finds no `dailyLimit` usage in the dashboard). The tracker retries 429s three times and silently drops (`public/tracker.js:155, 171-184`). Detecting a tripped breaker then becomes hours of guesswork for the exact customer most likely to hit it.
2. **Oversized exports point to an operator procedure that does not exist in the docs.** `GET /sites/:sid/export` rejects >10,000 rows with 413 and the message "Use the operator D1 export procedure." (`apps/worker/analytics.ts:567-580`). No procedure named in `docs/operations/` matches that claim (`deployment.md` / `data-recovery.md` contain no `wrangler d1 export`/operator export steps; the only mention is historical research in `docs/research/deepseek-review.md:322,382`). A first customer importing >10k events hits a dead-ended reference.
3. **Hash-navigation SPA pageviews are never counted, while the README claims SPA tracking.** `public/tracker.js:279-291` hooks only `pushState`/`replaceState`/`popstate`, and the pageview dedupe compares `location.pathname` only (`tracker.js:219-220`). For hash-router sites every route change is invisible beyond the first view. README:26 advertises "SPA tracking" without this boundary, and no browser test covers a hash router (see blind spots). Low-frequency pattern, but it will produce a "your numbers are broken" support report.
4. **No passkey inventory or removal.** Passkeys can only be added (`auth.ts:813-830`, `AccountView.tsx:257-284`). A user cannot list enrolled passkeys or revoke one from a lost/retired device; the only wholesale purge is account recovery (`auth.ts:441-453`), which requires a still-held recovery code. Recovery-code *regeneration* requires recent auth (`auth.ts:831-860`), so with all passkeys lost and recovery codes unread or exhausted, only raw D1 surgery remains — acceptable for a self-hosted alpha, but it is a lifecycle hole, and nothing documents it as a consequence.

These four are the flaws worth fixing on current source. Everything else I inspected (origin checks, role ranking, claim issuance under racing revocation, refund-before-payment "pending" classification, journal replay conflict rules, deletion allowlists) behaved as documented.

## Absent capabilities [2]

Ordered roughly by first-customer pain. Each is a *gap*, not a defect.

- **Account/workspace lifecycle completion.** No workspace deletion (only per-site deletion, `analytics.ts:534-547`), no account deletion, no owner transfer, no member role change (only owner can remove non-owner members, `auth.ts:980-1003`), no leave-workspace, no invite revocation (invites are irrevocable until their 24-h expiry; cleanup deletes only expired rows, `auth.ts:1027-1029`), and `users.disabled_at` is never written by any code path (grep-confirmed). The plan already flags "complete workspace/account deletion need review" (`current-product.md:11` and priority 4.4); it is accurate. For a first freelancer-customer this mostly costs nothing; it becomes blocking the moment a team actually forms or an owner loses a passkey.
- **Activation/limit visibility.** First-event verification is partial (`lastEventAt` display). There is no "collector health" state: blocked hostname, 409 session conflicts, 429 quota, and `site_paused` are all invisible to the owner. The parent's current-product priority 4.3 "make activation and limits clear" is the right next product work, and flaw [1].1 is its concrete core.
- **Published metric definitions.** Definitions exist only as a per-response `coverage` string (`reports.ts:288-297`), e.g. bounce = session with exactly 1 pageview and 0 goals (outbound clicks do not un-bounce a session; `reports.ts:187-189` + sessions update in migration trigger), sessions counted from period start while pageviews use event dates, `avgDuration` includes still-active sessions, and aggregate `visitors` is deliberately `null` (`reports.ts:128`). These are defensible, but a customer reconciling against GA4/Plausible needs a real definitions page they can cite to their stakeholders, not a tooltip.
- **Long-horizon ranges despite existing rollups.** `daily_summaries` are rebuilt daily (`maintenance.ts:38-71`) and retained ~13 months, yet no report reads them (grep: writes/deletion only). Reports cap at 90 days of detail (`reports.ts:86-88`). This is the one "already paid for" capability sitting idle; a summary-based 13-month trend would cost no new collection work. Still a v1-or-later item: it needs its own definitions and expiry-proof UI (see Not-build list).
- **Collector abuse is bounded but coarse.** Anonymous intake is protected by a single 120/min-per-IP edge bucket shared by all collectors (`wrangler.jsonc` `simple.limit 120`, `index.ts:76-93`), hostname/origin allowlists, UA bot rejection exclude-list (`analytics.ts:286-292`), ±24 h/5 min timestamp windows, and per-site daily caps with atomic dedup. There is no OS/CDN-level bot scoring, no per-visitor-shard abuse separation, and no per-site abuse view, so a hostile hostname-matching guest could still consume the site's own 1,000/day allowance. Adequate for alpha; the honest boundary is already documented (`current-product.md:13` "no promise of perfect bot/spam exclusion"). If the real constraint materializes, the cheapest effective fix is a Cloudflare WAF/Bot-fight rule at the edge, not new D1 state.
- **API ergonomics / revenue trust polish.** The server money API is three endpoints with prose docs and no OpenAPI spec/typed client; refund *before* payment evidence is deliberately classified `pending` rather than rejected (`payments.md:15`, code confirmed), which is correct but is surprising to a first integrator and deserves a doc callout (it has one). Revenue queries cap at 100 records/oldest-100 pending (`revenue.ts:833-837`) with no pagination or server-side list endpoint; no test-mode keys or webhook replay tool. None of this blocks a first customer; all of it shapes "can I trust this with my books" perception.
- **No email/identity dimension at all.** Passkey-only with manual token invites; recovery only by one-time codes. Deliberate and good for privacy posture; for public v1 this is the single largest fork in product direction (see priorities).

## Optional ideas [4] and what NOT to build yet

The plan's own disposition already rejects the worst overcomplications (IP/UA fingerprinting, EU-only mode, KV-based strict counters, KV/R2/Analytics-Engine, multi-touch attribution, multiple payment vendors, AI summaries — `implementation-plan.md` agent-findings section). Endorsing those rejections: **do not build these now.** Challenge in the same direction against earlier research:

1. **Don't turn `daily_summaries` into a general long-range query engine.** Summary-based trend pages are tempting (rollups already exist), but a "13-month report" that silently mixes summary-only and detail-backed metrics would recreate exactly the coverage-confusion problem the current 90-day boundary was built to avoid, and the summaries expire >396 days anyway. If long-range trends are wanted, ship ONE aggregate-only "seen all months" chart with an explicit `definition_version=1, summaries only` label — or defer entirely until a customer asks.
2. **Don't add email delivery / password auth "because customers will need it."** Passkeys + manual recovery codes are a coherent, safe alpha posture; email introduces deliverability, spam, password reset lifecycle and consent surfaces that are strictly larger. Choose scope when choosing hosted public v1 (parent priority 4.5), not before.
3. **Don't build per-site quota configuration, tier/plan tables, or custom daily_limit editing yet.** `daily_limit` is a validated but uneditable column plus a hardcoded default; tiers would be premature before measured Cloudflare costs (all capacity evidence is still [3]). If a first customer outgrows the default, the operator can set it via D1; document that workaround instead of building an entitlement engine.
4. **Don't add saved views/scheduled reports/sharing/CSV-only revenue exports/cohort tools.** They widen surface in every direction (ACLs, retention, share links) without fixing the currently blocked "prove it works where the customer will use it" step.
5. **Don't implement visitor-level "verified people", returning-visitor claims or cross-page people in aggregate mode.** The current document-scoped design is the privacy posture; weakening it to chase parity with Plausible metrics would undo the product's strongest differentiator while competitors' claims don't match their own physics either.

## Test blind spots (verified by grep against current tests; not a checklist)

1. **`installation_quota_exceeded` is never exercised.** Tests confirm site-quota atomicity (`analytics.test.ts:205`) and that installation usage increments (`analytics.test.ts:112`), but the request-level 429 path for the global breaker has no fixture — the exact breaker flaw [1].1 conflates.
2. **The 10,000-row export boundary is untested.** No test references `export_too_large` or a 10,001-row case; the 413 path and its message path [1].2 ship unverified.
3. **Invite capacity caps are untested.** The 100/workspace / 1,000 total invitation ceilings (`auth.ts:900`) are guarded by SQL but no test drives them; the live 429 failure path and its message ship unverified.
4. **Hash-router navigation is absent from all five browser flows** (they use canonical-path SPA navigation), matching flaw [1].3.
5. **The dataset of UAs used for bot exclusion is one regex; no test covers a real crawler UA or the 202-vs-drop semantics for an excluded UA with otherwise valid event**, so the boundary "bot silently 202'd vs accepted" is only code-reviewed.

Also confirmatory, not blind: prior reviews' fixed items have fixtures (concurrent key admission, ordered deletions, journal 1,005-row export, competing-pause retry classification) — these remain in place at `80be717`.
